=================
系统值
=================

应用程序要显示的状态，几乎总有一部分不属于自己：电池电量属于电量计，
当前时间属于 RTC 或手机，未读消息数属于通知服务。如果每个界面各自去调
用驱动，移植会变成噩梦——每块新板子都要满足每一种发明，应用反过来依赖
驱动头文件，而自身会变化的值只能靠轮询。本章介绍的这层抽象把这些问题
收拢到一处：应用只面对标准 key，平台相关的部分全部留在移植层。

应用和平台之间的往来只有两种方向。向上是应用主动发起的：界面用
``gui_sysval_get_request()`` 询问一个值，用 ``gui_sysval_set_request()``
请求改动一个值，两者都立刻返回一个 ID，真正的结果稍后由移植层交给
框架，再由框架在 GUI 线程上通过回调送给应用。向下是平台主动发起的：
驱动发现某个值变了，用 ``gui_sysval_publish()`` 报上来，框架转给所有用
``gui_sysval_subscribe()`` 订阅了这个 key 的界面。两条路径都不需要应用
知道是哪个驱动在服务它。

系统值里每个参与者都是以下三种角色之一。

.. list-table::
   :header-rows: 1
   :widths: 16 28 56

   * - 角色
     - 是谁
     - 职责
   * - 使用方
     - 应用、控件
     - 只知道 key 名。读、写、订阅，从不接触驱动。
   * - 生产方
     - 驱动、传感器任务、服务
     - 拥有该值。值变化时发布新值。
   * - 适配器
     - 移植层
     - 在特定平台上实现某个 key：应答读取和写入。

一个模块常常同时扮演后两者。电量计的移植层注册适配器让应用按需读取，
同时每次电量真正变化时发布一次；把两件事放在同一处，才能保证读取和
订阅得到同一个答案。

每个 key 的类型、访问权限、单位和范围由 :doc:`keys` 中的目录逐条固定。
两条规则让同一份目录能跨产品使用：声明一个 key 不等于注册它，适配器只
注册平台支持的 key，其余一律以 ``GUI_SYSVAL_REQUEST_INVALID`` 拒绝，界
面因此可以在没有编译开关的情况下探测可选能力；缺失数据不是值，没有读
数的 key 应答 ``GUI_SYSVAL_STATUS_ERROR`` 且不带值，零始终是一个真实的
零。

植层如何实现一个 key、应用如何读取和订阅，以及可直接运行的示例。
