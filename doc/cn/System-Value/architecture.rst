.. _System-Value-Architecture_CN:

==========================
架构设计
==========================

本章先定义系统值使用的 key 目录，再跟踪一个值从驱动发现它发生变化，
一直到显示它的控件被更新，并解释每一步为什么这样设计。


.. _System-Value-Keys_CN:

key 目录
----------------------

key 是命名一项状态的小写 ASCII 路径。这份目录定义在
``realgui/sysval/gui_sysval_keys.h`` 中，那里是权威参考：每个 key 都带有
类型、访问权限、单位和范围的注释块。本节说明如何阅读这些定义，以及如何
添加自己的 key。


如何阅读一个定义
~~~~~~~~~~~~~~~~~~~~~~

.. literalinclude:: ../../../realgui/sysval/gui_sysval_keys.h
   :language: c
   :start-at:  * Latest valid heart-rate measurement.
   :end-before: #define GUI_SYSVAL_KEY_HEALTH_HEART_RATE
   :prepend: /**
   :append: */

请使用 ``GUI_SYSVAL_KEY_*`` 宏，不要直接写字符串。正是这个宏让笔误变成
编译错误，而不是一次运行时静默失败。


目录分组
~~~~~~~~~~~~~~~~~~~~~~

.. list-table:: 顶层命名空间
   :header-rows: 1
   :widths: 20 80

   * - 命名空间
     - 内容
   * - ``system/``
     - 本地时间与日期、时间格式、时区、语言、免打扰。
   * - ``device/``
     - 产品名称、型号和固件版本。
   * - ``power/``
     - 电量、充电状态、剩余时间、电压、外接电源、省电模式。
   * - ``display/``
     - 亮度、息屏超时、常亮、抬腕亮屏。
   * - ``audio/`` 与 ``haptics/``
     - 音量、静音、振动。
   * - ``connectivity/``
     - 蓝牙与 Wi-Fi 的使能状态和连接状态。
   * - ``health/``
     - 计步、心率、血氧、血压、体温、压力、睡眠与佩戴状态。
   * - ``workout/``
     - 状态、模式、已用时、步数、距离、卡路里、心率汇总。
   * - ``weather/``
     - 城市、天气状况、温度与湿度，附带数据时效。
   * - ``media/``
     - 音乐状态、音量、标题与艺术家。
   * - ``notifications/`` 与 ``alarms/``
     - 仅有数量。条目本身需要一个列表接口，超出了单个值 key 的范围。
   * - ``stopwatch/`` 与 ``countdown/``
     - 状态、已用时间、设定时长与剩余时间。
   * - ``reminders/``
     - 久坐与喝水提醒，及其间隔。


按类型读取值
~~~~~~~~~~~~~~~~~~~~~~

目录保证了类型，因此该读哪个成员是预先确定的。但仍然要先检查值指针和状
态：受支持但当前没有读数的 key 会以错误且不带值的方式应答，不检查就访
问联合体会用到过期或空的成员。

.. list-table:: 联合体成员
   :header-rows: 1
   :widths: 25 25 50

   * - 类型
     - 成员
     - 示例 key
   * - ``GUI_SYSVAL_TYPE_BOOL``
     - ``value->data.b``
     - ``GUI_SYSVAL_KEY_POWER_BATTERY_CHARGING``
   * - ``GUI_SYSVAL_TYPE_INT``
     - ``value->data.i``
     - ``GUI_SYSVAL_KEY_POWER_BATTERY_LEVEL``
   * - ``GUI_SYSVAL_TYPE_STR``
     - ``value->data.s``
     - ``GUI_SYSVAL_KEY_WEATHER_CITY``

字符串最多容纳 ``GUI_SYSVAL_STR_MAX - 1`` 字节，且总是以 NUL 结尾。过长
的文本由适配器在 UTF-8 字符边界上截断，因此字符串可能比平台自身的文本
短，但绝不会在字符中间被切断。


新增产品专用 key
~~~~~~~~~~~~~~~~~~~~~~

这份目录覆盖的是许多产品共有的状态。任何只属于某个产品的状态，都应放在
私有命名空间下，且不得重新定义标准 key：

.. code-block:: c

   /* 产品专用：工牌 LED 动画速度。 */
   #define GUI_SYSVAL_KEY_BADGE_LED_SPEED "badge/led/speed"

新增 key 的规则：

- 描述可观察的状态，而不是动作。名为 ``reboot`` 的 key 是穿着状态外衣
  的命令；应该用带 ``set_request`` 的适配器，配一个
  ``system/reboot_pending`` 这样的状态 key。
- 把单位写进文档，不要写进路径。目录里有一个历史遗留的例外
  ``power/battery/remaining_seconds``，为兼容性保留。
- 用定点整数而不是浮点数。以 0.1 度为单位的 ``365`` 就是 36.5 度，单位
  那一行会说明这一点。
- 取值集合很小的状态，用字符串承载文档中列出的某个小写标记，而不是用整
  数配头文件里的枚举。
- 不要为只有某一个界面会读的值新增 key。一个本地缓存变量更简单，也不会
  扩大移植面。


注意事项
~~~~~~~~~~~~~~~~~~~~~~

**没有原子快照。** 每个请求独立应答。读三个 key 并不给出一致的系统视图：
你读到的电量可能比你接着读到的充电状态早一秒。设计界面时，要让每个值都
能被独立渲染。

**可选 key。** 声明一个 key 不等于注册它。适配器只注册平台支持的部分，
其余全部应答 ``GUI_SYSVAL_REQUEST_INVALID``。要把它理解成“这个产品没有
这项功能”，而不是一次临时故障，也不要重试。

**零是一个值。** ``0%`` 电量、``0`` 步和 ``0`` 条未读消息都是真实的。缺
失数据有它自己的上报路径——一个不带值的错误状态——因此界面不能把零当作
“未知”。


两条路径，一个模块
----------------------

系统值有两条相互独立的路径。它们只共享 key 目录和适配器注册表，其余毫
无关联。

读取路径是请求/应答：应用提问，移植层恰好回答一次。变化路径方向相反，
是发后不理：驱动上报，所有订阅了这个 key 的订阅者都会收到。

一个界面通常两者都用。它可以只订阅一次、之后不再读取；也可以订阅后再
读一次以填充第一帧，因为订阅只承载变化，否则在有事发生之前画面会是
空的。


队列不是传输通道
----------------------

最直观的实现是把值放进一条 GUI 消息，让 GUI 线程取出来。HoneyGUI 没有
这样做，因为消息队列长度有限，丢一条消息就是丢一个值。

取而代之，两条路径各自维护一条链表：

- ``gui_sysval_respond()`` 把已应答的请求移到 **完成链表**。
- ``gui_sysval_publish()`` 把值复制进 **通知链表**。

数据本身从不经过消息槽。单槽队列只被当作锁使用，只发送一条 GUI 消息用
于唤醒空闲的 GUI 线程。如果这条唤醒消息因为队列已满被丢弃，说明 GUI
线程本来就在忙碌，服务端钩子会在下一帧取走链表。两种情况都不会丢值。

``sysval_dispatch()`` 每帧由服务端钩子执行一次；GUI 线程空闲时由唤醒
消息触发执行。它是唯一会调用回调的地方。


序列号
----------------------

每一次发布都会分配一个序列号。订阅会记录它创建时刻的当前序列号，之后
只接受更大的序列号。以下四种行为都由这一条规则直接推出。

**订阅之前发布的变化不会被重放。** 订阅从该序列号之上开始。如果订阅创
建时，某个变化还停留在通知链表里，它的序列号更大，会被投递。这条边界
的判据是“GUI 线程是否已经见过”，而不是“调用发生在什么时刻”——后者是
唯一与用户所见一致的判据。

**一阵突发会合并成一次投递。** 对仍在链表中的 key 再次发布时，是就地
替换值而不是追加。订阅者只会被调用一次，拿到最新的值。因此突发很廉价，
显示也不会出现它渲染不了的中间态。

**已经显示在屏幕上的值会被丢弃。** 投递之前，GUI 线程会把该值与它上次
为该 key 投递的值比较，相同则不调用任何回调。正是这一点避免了可写 key
把自己的变化通知又喂回执行写入的控件：一个在拖动时写音量、同时又订阅
音量的滑块，不会和自己打架。

**顺序只在单个 key 内保证。** 同一帧内发布的两个 key，投递顺序可能颠倒。
系统承诺的是每个 key 的最新值，而不是全局时序——正是这一点换来了合并
能力。


过期的读取
----------------------

“订阅后再读一次”有一个朴素实现会掩盖的竞态。移植层可能应答很慢；此时
一个变化被发布并投递了。当应答终于到达时，它携带的是**更旧**的值，把
它应用上去会让屏幕往回跳。

``gui_sysval_get_request()`` 会记录读取开始时的当前序列号。派发时，如果
该 key 更新的值已经被投递过，应答会被上报为
``GUI_SYSVAL_STATUS_STALE`` 而不是 ``GUI_SYSVAL_STATUS_OK``。值仍然会
传递，以便没有订阅的调用方也能使用；但同时也订阅了的界面就知道应该
保留手里已有的值。


线程模型
----------------------

生产方一侧没有限制：``gui_sysval_publish()`` 和 ``gui_sysval_respond()``
可以从任意线程调用。

使用方一侧不是：请求由 ``gui_sysval_get_request()`` 和
``gui_sysval_set_request()`` 创建，订阅由 ``gui_sysval_subscribe()`` 和
``gui_sysval_unsubscribe()`` 管理，全部在 GUI 线程上。这种不对称是刻意
的。订阅回调会更新控件，而控件只能在 GUI 线程上操作；若允许在别处创建
订阅，只是把错误推离了它的成因。

共享链表的保护使用移植层自己的消息队列作为单槽锁，与 HoneyGUI 其余部
分保护内存所用的原语相同。在单线程、没有消息队列的移植层上，这把锁退
化为空操作。


生命周期
----------------------

订阅会一直有效，直到被取消。系统无法得知它指向的 ``user_data`` 已被释
放，因此会访问控件的回调，必须在该控件销毁之前取消订阅。

``gui_sysval_unsubscribe()`` 可以在回调内部安全调用：对该订阅者的投递
立即停止，内部记录在派发结束时释放。用同一个句柄调用两次不受支持；调用
返回后句柄即失效。
